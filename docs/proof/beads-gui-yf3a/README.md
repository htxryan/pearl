## Proof-driven bug fix (v6/v7)

Re-gathering proof surfaced a real systemic z-index bug across **6** overlay primitives:

- **Symptom**: Combobox popups (label-picker, assignee-picker) and Select/Popover/DropdownMenu popups were paint-stacked **below** the Dialog backdrop scrim — the popup options rendered to DOM but were invisible. Confirmed via `elementsFromPoint` showing the `class="fixed inset-0 z-50 bg-black/80"` backdrop as the topmost element where popup options should be.
- **Root cause**: BaseUI's `<Popup>` element has `position: static`, so `z-index` on it is a no-op. The stacking-context-bearing element is the `<Positioner>` (which is `position: absolute`).
- **Fix**: moved `className="z-[60]"` from `Popup` → `Positioner` across `combobox.tsx`, `popover.tsx`, `select.tsx`, `dropdown-menu.tsx` (×2 sub+root), `label-picker.tsx`, plus the fixed-position `assignee-picker.tsx` panel.
- This fix is what makes the v7 popover/virtualization screenshots possible — pre-fix screenshots showed an empty backdrop, post-fix screenshots show populated popups.

### Layout fixes (v6)

User-reported regressions from earlier proof passes:

- **Page content width** — earlier screenshots like `v2-19-settings-page.png` showed the right half of the viewport blank-white. Cause: `AppShell` outer container was width-constrained instead of `w-screen`. Fix in `app-shell.tsx`. Verified by:
  - `v6-fix-01-list-view-fullwidth.png`
  - `v6-fix-02-settings-fullwidth.png`
  - `v6-fix-03-board-fullwidth.png`
  - `v6-fix-04-graph-fullwidth.png`
- **Command palette modal height** — opened at fixed height that ran off the bottom of short viewports. Fix in `command-palette.tsx`: switched outer to `flex flex-col max-h-[60vh]` so the results list owns the overflow. Verified by:
  - `v6-fix-05-command-palette-bounded.png` — bottom edge clears the viewport
  - `v6-fix-06-command-palette-scrolled.png` — list scrolls inside the bound

### Theme matrix — all 15 VSCode themes (v7)

Captured against the showcase route after calling `window.__pearlSetTheme(<id>)` and verifying via `getComputedStyle(document.documentElement).getPropertyValue('--background')` that each cell renders distinct theme tokens. Earlier v6 attempts produced 15 byte-identical screenshots because the script passed bare names (e.g. "monokai") instead of the canonical IDs (e.g. "vscode-monokai") — `getTheme()` silently fell back to the default. ### Theme adaptation in overlays (v7)

Proof that the migrated Dialog primitive picks up theme tokens (not just the page chrome):

- `v7-dialog-theme-light-plus.png` — Create Issue dialog, Light+

Theme is applied by setting `localStorage.setItem("pearl-theme", id)` BEFORE navigation so the `applyTheme()` mounting effect picks it up — proves the theme bridge wires correctly through React Query Provider → ThemeProvider → CSS custom properties.
